- [x] **Fixed word-order search bug**: searching "adobo chicken" didn't match "Chicken Adobo" because the whole query was matched as one literal substring. Now splits the query into words and ANDs a separate `ILIKE '%word%'` per word — order and adjacency no longer matter. Applied to both `/api/foods/search` and `GET /api/recipes?q=`, verified live (reversed order, non-adjacent words, and mixed case all match correctly). Case was never actually the problem — `ILIKE` is already case-insensitive; lowercasing the stored `name` was considered and rejected since it would've thrown away real display casing for zero search benefit
- [x] **`pg_trgm` GIN index + typo-tolerant fuzzy search** — enabled the `pg_trgm` extension on Neon, added `gin_trgm_ops` GIN indexes on `foods.name` and `recipes.name` (accelerates the `ILIKE` matching from the word-order fix too). Each query word matches on exact `ILIKE` substring OR a pg_trgm fuzzy match — a typo like "chiken" still finds "Chicken Adobo"
- [ ] The fuzzy branch isn't index-accelerated yet — the GIN trgm index matches on raw `name`, but the query lowercases both sides for case-insensitivity, so an expression index on `lower(name)` would be needed to speed up that specific branch. Fine at current scale (the `ILIKE` branch, which is accelerated, already narrows most real queries)
- [x] **Real bug found and fixed: fuzzy search was returning unrelated foods** — user reported searching "banana" in the recipe ingredient picker surfaced Chicken Breast, Salmon Fillets, and Adobo. Root cause: the original fuzzy check used `word_similarity(word, whole_name_or_brand)` at threshold 0.3 — comparing a short word against an *entire* multi-word string. "banana" has heavy internal letter repetition (an/na/ana), giving it very few distinct trigrams, so matching just one or two common ones against a long unrelated string was enough to score above 0.3 (verified: 0.33-0.5 against completely unrelated text). Rewrote to compare the query word against each *individual* word of name/brand instead (`similarity()`, word-vs-word, via `unnest(string_to_array(...))`), and raised the threshold to 0.4 — verified against real data this blocks all 7 observed false positives (they score 0.07-0.14, occasionally 0.3 for a visually-similar word) while still catching the most common typo patterns (missing a letter, adjacent-key slip both score 0.5+). Applied to both `/api/foods/search` (name + brand) and `GET /api/recipes?q=`
- [ ] **Known, disclosed tradeoff of the 0.4 threshold**: rarer typo patterns (transpositions, removing a middle letter — e.g. "adbo" for "adobo" scores 0.375, just under the cutoff) can now slip through uncaught, where the old looser threshold would have caught them — at the cost of also catching every false positive like the banana case. Chose fewer false positives over maximum typo recall; not revisiting unless it proves too strict in practice
- [x] **Search now also matches `foods.brand`, not just `name`** — found while checking Filipino canned-goods brand coverage: some Open Food Facts products don't repeat their brand in the name at all (`product_name: "Corned Beef"`, `brand: "Argentina"`), so name-only search silently missed brand-only queries. Each word now matches name OR brand, exact-or-fuzzy, same logic as before. Verified live: brand-only ("argentina"), mixed brand+name ("argentina beef"), and a typo'd brand ("argentna") all correctly find it; confirmed no crash/false-positive from foods with a null brand
- [x] Confirmed live (not assumed) that major Filipino canned-goods brands exist on Open Food Facts: Ligo (19 products), Purefoods (135), Century Tuna (70), Mega Sardines (27), Argentina (14). USDA has none of these — it's US-only. Two brands (555, CDO) couldn't be confirmed either way — OFF rate-limited the check (503s) before an answer came back, not necessarily absent
